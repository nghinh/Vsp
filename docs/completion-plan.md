# VSP Completion Plan

**Date:** 2026-08-06
**Scope:** `apps/api`, `apps/mobile`, `apps/portal`, `apps/watch_apple`, `apps/wear-os`, `infra/`, `tools/`, live `vsp_postgres` DB, live API on `:8080`
**Status of this document:** audit + plan only. No code was changed.

---

## 0. Verdict

**Not releasable.** Four things independently block launch, and each would block it alone:

1. **The golf course data is fabricated.** 831 of 900 holes are synthetic geometry generated by a demo seed script, stamped `C_VERIFIED_SATELLITE` / `VERIFIED` / confidence 95%. All 50 courses share one identical invented scorecard. This is the product's foundation and it is not real.
2. **A clean clone of the repo does not compile.** A Maven `target/` ignore rule silently excludes a Flutter feature directory that reachable code imports.
3. **The core offline loop is broken end to end.** Round/score/shot sync posts to three endpoints that do not exist; the round-completion screen is unreachable; course packages point at a domain that does not resolve.
4. **The migration set cannot produce the schema the application runs on.** The app has only ever run on a Hibernate-generated schema. Production is configured to use Flyway.

A secondary theme runs through all of it: **the dangerous defects here look finished.** The badge says VERIFIED, the audit log says ALERT_SENT, the sync indicator goes green, the portal shows a populated pin-position grid, the test suite reports 882/1262 passing. In each case the underlying thing did not happen.

The application *code* is in noticeably better shape than its data, configuration, and wiring. Most of what follows is plumbing that was written and never connected, not logic that was written wrong.

## 3. P0 — blocks a real golfer playing a real round

### P0-1. The course data is fabricated, and labelled VERIFIED

**This is the most important finding in the audit.** Everything else is fixable in weeks; this is the product.

**What is broken.** `scripts/dev/seed_courses_vn.sql:97-134` generates every hole arithmetically:

```sql
plen := CASE p WHEN 3 THEN 155 + (h*3) WHEN 5 THEN 480 + (h*4) ELSE 360 + (h*2) END;
tlon := facilities[i][3]::float8 + (h * 0.0008);
tlat := facilities[i][4]::float8 + (h * 0.0006);
glat := tlat + (plen / 111000.0);
...
'C_VERIFIED_SATELLITE','VERIFIED',95.0,'SEED','VSP Seed','CC-BY-4.0',
```

The green is placed exactly `plen` metres **due north** of the tee. The tees march in a straight diagonal line at a fixed 0.0008°/0.0006° step. The script's own header admits it: *"hole tee/green points are synthesised near the facility for GPS demo"*. It then stamps that demo data `VERIFIED`, `C_VERIFIED_SATELLITE`, confidence `95.0`, licence `CC-BY-4.0`.

**Evidence gathered (live DB):**

```
holes by source:
  SEED                       831   C_VERIFIED_SATELLITE / VERIFIED        / CC-BY-4.0
  osm:way/*                   61   D_UNVERIFIED_COMMUNITY / PENDING_REVIEW / ODbL-1.0
  derived:facility-offset      8   D_UNVERIFIED_COMMUNITY / UNVERIFIED

Bearing tee→green on SEED holes: exactly 0.00°  (due north, every hole)
Measured vs stated length:  SEED avg error 1.1 m   |   OSM avg error 41.1 m
   (real holes disagree with the card because of doglegs; synthetic ones cannot)

Par/length signature across all 50 courses:  1 distinct signature
   4:362, 5:488, 4:366, 3:167, 4:370, 4:372, 5:508, 3:179, 4:378, 4:380,
   4:382, 3:191, 5:532, 4:388, 4:390, 3:203, 4:394, 5:552
42 of 50 courses share byte-identical relative hole offsets.
```

Every one of the 50 named Vietnamese courses — BRG Kings Island, Long Thành, Vinpearl, Dalat Palace — is the *same* fabricated 18-hole layout translated to a different origin.

**Worse: the fabricated scorecard overwrites the real courses too.** Long Thành has 16 genuine OSM-mapped holes, and its stated yardages are still the synthetic template:

| Hole | Stated | Measured from real geometry | Error |
|---|---|---|---|
| 2 | 488 m | 377.1 m | **+110.9 m** |
| 3 | 366 m | 436.9 m | **−70.9 m** |
| 7 | 508 m | 438.6 m | +69.4 m |
| 15 | 390 m | 320.7 m | +69.3 m |
| 17 | 394 m | 459.2 m | −65.2 m |

**Why nothing warns the golfer.** Three independent gates all fail open:

1. `CourseSearchServiceImpl.enrichDataFreshness` reads `verification_status` from `data_versions`. All 50 rows are `PUBLISHED` / `VERIFIED` (seeded by the same script). Live API confirms: **all 50 search results return `verificationStatus: VERIFIED`.**
2. `apps/mobile/lib/domain/models/data_quality.dart:133` derives the badge. Class C → `estimated`, which is the honest outcome — but it is driven by the *course-level* class, and `isStale` (>30 days) never fires because the seed was published `2026-08-05`.
3. `apps/mobile/lib/features/hole_map/domain/hole_geometry_coverage.dart:33` decides whether to draw a vector map by **presence** of geometry, not provenance. Every synthetic hole has a derived green and a derived fairway, so `hasStrategicGeometry` returns `true`, the satellite fallback never triggers, and the "unsurveyed hole" banner never shows.

The file's own comment says *"Only 69 of ~900 holes have surveyed coordinates"* — the intent was right; the implemented gate does not test for it.

**Derived geometry is equally synthetic:**

```
greens:            840 × derived:green-point-extent  → identical circles, 611–612 m², 33 vertices
                    91 × real OSM polygons           → 428–496 m², 14–17 vertices
fairway_segments:  900 / 900 derived corridors       → zero real fairway data
```

With `pin_positions = 0`, `hole_geometry_coverage.greenAnchor` falls back to *"the centroid of the green polygon"* — which for 840 of 931 greens is the centre of a synthetic 14 m circle placed at a synthetic point. **The distance a golfer reads is fabricated from end to end.**

**Full data inventory (live DB, verified):**

| Table | Rows | Reality |
|---|---|---|
| `courses` | 50 | 21 real OSM facilities, 29 pure seed |
| `holes` | 900 | **61 real**, 831 synthetic, 8 offset-derived |
| `greens` | 931 | **91 real polygons**, 840 identical derived circles |
| `fairway_segments` | 900 | **0 real** — all derived corridors |
| `bunkers` | 332 | all real OSM — but on only **60 holes across 8 courses** |
| `water_hazards` | 45 | 40 Sentinel-2 NDWI, 5 OSM — 8 courses |
| `tee_sets` | 150 | 3 per course, all `total_par 72`, no yardages |
| `tee_boxes` | **0** | tee selection changes nothing |
| `pin_positions` | **0** | |
| `green_conditions` | **0** | no green speed / stimp anywhere |
| `penalty_areas`, `cart_paths`, `landmarks`, `out_of_bounds` | **0** | |

**42 of 50 courses contain no real geometry at all.**

**What is needed for the app to be genuinely usable on a real round:**

| Need | Status | Obtainable how |
|---|---|---|
| Tee + green coordinates per hole | 61/900 | Manual digitisation from satellite → Class C |
| Per-tee boxes and per-tee yardages | 0 | Digitisation + course scorecards |
| Green outline (front/centre/back) | 91/931 | Digitisation |
| Bunker / water carry distances | 60/900 holes | Digitisation |
| Real scorecard par + yardage | 0/50 courses | Course scorecards (public) |
| **Pin position (daily)** | 0 | **Course partnership only** |
| **Green speed / stimp (daily)** | 0 | **Course partnership only** |
| Course conditions, closures, alerts | 0 | **Course partnership only** |

**Recommended plan:**

- **Immediately (½ day):** stop the lie. Re-stamp all `source='SEED'` rows to `D_UNVERIFIED_COMMUNITY` / `UNVERIFIED`, and change `hole_geometry_coverage` to gate on provenance rather than presence so synthetic holes fall back to satellite + measuring. Correct labelling is a prerequisite for shipping *anything*.
- **Phase 1 (4–6 wks):** pick 5–10 launch courses. Digitise tees, greens, bunkers, hazards and per-tee yardages from satellite imagery + published scorecards. Roughly 3–5 h per course for a trained operator. Extend `tools/course-digitization` (which is genuinely well built) to cover tee boxes. Target Class C, honestly labelled.
- **Phase 2 (partnerships, not engineering):** pin positions and green speed change daily and can only come from the courses. This needs a signed partnership, a working portal ingest (see P1-11 — the pin-position page is currently a mockup), and a daily operational routine at the club. **Ship without them** and present distance-to-green-centre only, clearly labelled — do not present a pin number you do not have.
- **Do not launch nationwide.** 50 fake courses is worse than 8 real ones.

**Effort:** 6–10 weeks engineering + digitisation for a credible 10-course launch; pin/green-speed indefinitely gated on partnerships.
**Blocks a real round: yes — this is the round.**

### P0-3. A release build of the mobile app cannot function or be shipped

Five independent defects, any one fatal.

1. **API base URL is compile-time localhost.** `apps/mobile/lib/core/network/api_client.dart:79`, `lib/data/api/performance_api.dart:45`, `lib/data/api/weather_api.dart:39` — all `String.fromEnvironment('VSP_API_BASE_URL', defaultValue: 'http://localhost:8080')`, `const`, no `kDebugMode` guard anywhere in `lib/`. Nothing in the repo passes the define — no CI step, Makefile, or fastlane config. Compounded by `targetSdk = 36` blocking cleartext and no iOS ATS exception, so the call is refused before it leaves the device.
2. **Tournament features are hardcoded to an unroutable host.** `lib/application/tournament/tournament_service.dart:18` — `const String _baseUrl = 'https://api.vsp.local'`. Not even a define; `.local` is the mDNS reserved TLD. No code-free fix.
3. **iOS terminates on first GPS use.** `apps/mobile/ios/Runner/Info.plist` has **zero** permission usage descriptions — no `NSLocationWhenInUseUsageDescription` — while `lib/data/services/location_service_impl.dart:103-109` requests location. On iOS this is process termination, not a denial. Also missing: `PrivacyInfo.xcprivacy` (mandatory since May 2024; upload fails ITMS-91053), `Runner.entitlements`, `CFBundleURLTypes`.
4. **Android release is debug-signed.** `apps/mobile/android/app/build.gradle.kts:28-34` is the untouched template TODO. Play rejects debug-signed uploads. `apps/wear-os` has no release `signingConfig` at all and `targetSdk = 34`, below Play's floor.
5. **Launcher icons are the stock Flutter logo**, MD5-identical to the SDK template; app label is `vsp_mobile`; version still `0.1.0+1`.

**On the Mapbox token specifically** — this is the *best*-engineered part of the codebase and it does **not** crash. `lib/features/basemap/domain/satellite_imagery_config.dart:121` reads `String.fromEnvironment('MAPBOX_ACCESS_TOKEN')` with no default; `resolve()` falls through to an `unavailable` sentinel; `satellite_style_builder.dart:59` only adds the raster source when available, so MapLibre still gets a valid style with a solid background; three widget guards then show a localised `UnsurveyedNoImageryView`; and `toString()` is overridden so the token can never reach a log. **But nothing passes the define**, so satellite view is absent in every build that exists today — and combined with P0-1, that means the map shows "imagery unavailable" over fabricated geometry almost everywhere.

**Effort:** 1–2 weeks (signing keys, Apple provisioning, privacy manifest, icons, build scripts that actually pass the defines). **Blocks: yes.**

### P0-4. Offline sync posts to three endpoints that do not exist

**What is broken.** `apps/mobile/lib/infrastructure/sync/idempotency_client.dart:79-100`:

```dart
case SyncEventType.roundCreate:
case SyncEventType.roundComplete:
  return '/api/rounds/${event.entityId}/sync';     // 404
case SyncEventType.scoreUpdate:
  return '/api/scores/${event.entityId}/sync';     // 404
case ... shotStarted/shotEnded/shotEdited/shotDeleted/shotsMerged:
  return '/api/shots/${event.entityId}/sync';      // 404
```

Two compounding defects. **Wrong prefix** — no other mobile call uses `/api`, and the API has no context path (verified: `POST /auth/login` → 200). **Wrong shape** — there is no `…/sync` route for rounds or shots at all. The only sync route on the server is `POST /scores/sync` (`ScoreController.java:63`) — collection-level, no `{id}`. Stripping `/api` still 404s.

Confirmed live against the running API with a valid golfer token: all three return 404 (control: `/markets` → 200).

**Failure mode.** `sync_worker.dart:225` classifies 4xx as `isPermanentFailure` → `markFailed`, no retry. The events are not silently discarded — the golfer does see a failed sync status — but the data never reaches the server and manual retry hits the same 404. Every queued round create/complete, every score update, and all five shot event types fail permanently.

The code knows the right target: `scorecard_screen.dart:103` comments *"syncs to `POST /rounds/{roundId}/shots`"* — an endpoint that **does** exist (`ShotController.createShot`). The sync client just never points at it.

**Effort:** 3–5 days — repoint scores at `POST /scores/sync`, shots at `POST /rounds/{roundId}/shots`, and build the round create/complete sync path (or route it at the existing `POST /rounds` + `POST /rounds/{id}/complete`). **Blocks: yes.**

### P0-6. Offline course packages do not exist

The "download this course for offline play" product is non-functional at every layer.

- **The CDN does not exist.** All 8 manifests point at `https://cdn.vnptgolf.vn/...`. Verified: `nslookup` → **NXDOMAIN**; `curl` → connection failure. The host is hardcoded, not env-configurable, at `lib/data/services/course_package_download_service.dart:374` and in `course_package_update_service.dart`. The server's own `GET /packages/**` endpoint (`PackageFileController:54`, deliberately `permitAll` "in place of a CDN") is never called.
- **Only 8 of 50 courses have a manifest**, and every one has `package_size_bytes = 0`. `package_file_entry` and `package_build_job` are both empty.
- **The API reports all 50 as downloadable.** `CourseSearchServiceImpl:203`:
  ```java
  dto.setHasPackage(dataVersionRepository.findLatestPublishedByCourseId(course.getId()).isPresent());
  ```
  It checks for a published *DataVersion*, not a *package manifest*. Live API confirms **`hasPackage: true` on all 50 results.** This is the same "empty packages reported as offline ready" defect a previous session believed fixed — the fix did not reach this path.
- **Checksum verification always passes.** `lib/data/services/package_readiness_service.dart:200`, `_spotCheckChecksum`: `// For now, return true` — so `PackageReadinessReason.checksumMismatch` is unreachable and its message *"Course data is corrupted. Please re-download."* can never be shown. Server-side, `PackageGenerationService.java:414` computes the manifest checksum as `sha256Hex(courseId + ":" + version + ":" + totalSize)` — a hash of metadata, not content. The integrity chain is fake at both ends.
- **The download screen throws on open.** `lib/presentation/screens/course_download_screen.dart:85` — `throw UnimplementedError('Inject SharedPreferences via provider')`, called from `initState`. It is a live nav target from `course_search_screen.dart:628`. Same stub in `download_management_screen.dart:250`. Tapping a course to download it produces a red screen.
- **Publishing silently skips the package build.** `PublishServiceImpl.java:201` wraps `queueBuildForCourse` in `catch (Exception e) { log.warn(...) }` and returns `PUBLISHED` with `buildJobId=null`. The portal does not surface the null.

**Effort:** 2–3 weeks — provision or stand down the CDN (routing at the existing `/packages/**` endpoint is the cheap path), make the host configurable, fix `hasPackage`, implement real content checksums, wire the download screen's dependencies. **Blocks: yes** for offline play, which is the point of a golf app.

### P0-7. The Flyway migration set cannot produce the schema the app runs on

**What is broken.** `application.yml:16` sets `flyway.enabled: true`. Only `application-dev.yml:21-22` opts out, running `ddl-auto: update` instead. **Prod and staging inherit Flyway.** The application has therefore only ever run on a Hibernate-generated schema that no migration produces.

**Evidence — I diffed the migrations against the live database:**

```
Tables created by migrations : 56
Tables in the live database  : 67

Live but created by NO migration (13):
  shots, green_conditions, pin_positions_ops, draft_geometry_features,
  course_conditions_ops, market, market_config, data_license,
  data_license_redistribution_market, payment_booking_links,
  osm_golf_staging, osm_hole_match, sat_water_staging
```

Column-level drift too. `rounds` in the live DB has `course_id`, `tournament_id`, `tournament_policy_id`, `tournament_policy_version`. **No migration adds any of them** — `V13__rounds_and_scores.sql:4-14` has none. The entity acknowledges it in a comment: `Round.java:28` — *"TODO (Slice D gap): V13 migration does not include course_id column."*

Type divergence: `V16__facilities_courses_holes.sql:9,31,51` declares `id UUID`; the live `courses.id` is `bigint`. `V17` uses `hole_id UUID` while `V13`/`V20`/`V21` use `BIGINT`. `V16:15,35,55` stores geometry as `VARCHAR` with GIST indexes over `ST_GeomFromWKB(location::bytea)`.

`flyway_schema_history` no longer exists in the live DB — it was dropped by hand.

**Why nothing caught it:** `apps/api/src/test/resources/application-test.yml:8` uses H2 with `flyway.enabled: false` and `ddl-auto: create-drop`. **All 34 migrations are executed by zero tests.** And the CI step designed to catch exactly this — `ci-api.yml:71-78` "Migration dry-run", running `mvn flyway:dry-run` — is not a real Flyway goal, the plugin is not in the pom, and it is wrapped in `2>/dev/null || echo` *plus* `continue-on-error: true`. It is constructed so it cannot fail.

**Effort:** 1–2 weeks — regenerate the migration set from the current entity model as a new baseline, run migrations in tests against real Postgres, delete or fix the dry-run step. **Blocks: yes** for any deployment beyond one developer's laptop.

## 4. P1 — ships an embarrassment, or corrupts data

### P1-9. Authentication and authorization

Five distinct defects.

1. **Social login performs no signature verification.** `SocialTokenValidatorService.java:63-86` (Google) and `:108-143` (Apple) split the JWT and base64-decode the payload. No JWKS fetch, no signature check, no audience, no expiry. Apple's only gate is `issuer.contains("apple")`. Forge `{"sub":"x","email":"admin@vsp.local","iss":"apple"}` and you are that user. The method's own javadoc says *"validates the signature using Apple's JWKS keys"* — **it does not**. Currently mitigated only by accident: `/auth/google` and `/auth/apple` are absent from the `permitAll` list, so both 403. It becomes a full auth bypass the moment someone "fixes" that.
2. **The portal has no authentication and grants itself super-admin.** `apps/portal/src/auth.ts:13-14,18,34`:
   ```ts
   const DEV_TOKEN = "dev-portal-token";
   const DEFAULT_ROLES = ["COURSE_ADMIN", "SUPER_ADMIN"];
   export function getAuthToken() { return localStorage.getItem(TOKEN_KEY) ?? DEV_TOKEN; }
   export function getUserRoles() { ...; return [...DEFAULT_ROLES]; }
   ```
   No `import.meta.env.DEV` gate, no login route, no login page. Every role-gated element unlocks client-side for any visitor.

### P1-13. Test integrity: the suites are green, and green means less than it looks

The counts are honest: **882 API tests and 1262 mobile tests genuinely pass** (both re-run during this audit; portal adds 49). What they cover is the problem.

- **No test touches the real schema.** `application-test.yml` is H2 with `flyway.enabled: false` and `ddl-auto: create-drop`. All 34 migrations are executed by zero tests — which is exactly why P0-7 went undetected.
- **Only 8 of 86 Java test classes are `@SpringBootTest`.** 69 are plain unit tests with no Spring at all, so wiring bugs have almost no surface to be caught on. That is how the `MfaAttemptLimiter` bug — the previously-found self-fulfilling test — survived: it had two constructors, Spring could not choose, the whole application context failed to construct, and the test stayed green because it used the test-only constructor and never went through DI.
  - **Good news:** that exact pattern has no siblings. `MfaAttemptLimiter` is the only multi-constructor Spring bean in `src/main`, and there are **zero** `@MockBean`/`@MockitoBean`/`@TestConfiguration` substitutions in the Java suite.
- **The systemic sibling is worse, and the codebase documents it itself.** From `GeospatialServicePostgisTest.java:22-42`: *"`GeospatialServiceImplTest` mocks the `EntityManager` and `application-test.yml` is H2, so no test in this repository has ever sent one of these statements to PostGIS. That is precisely how `ST_SetSRID(:geom, :srid)` survived: ... PostgreSQL refuses the statement — while every one of these methods catches broadly and answers `null`/`false`/an empty list, so the caller is told 'no result', never 'the query could not run'."* **Auditing for that catch-broadly-return-empty pattern is the highest-value test work available.**
- **The ~48 tests that touch anything real can silently vanish.** 39 Java tests are `@EnabledIf`-gated on PostGIS reachability and 9 Flutter system tests self-skip when no API answers — with no "skipped" count. Worse, the auditor **observed the gate failing open on a machine where PostGIS was up**: `GeospatialServicePostgisTest` contributed 0 tests to the full-suite run, then ran 12 passing tests in isolation minutes later. A green 882 does not tell you whether the geospatial tests ran.
- **Critical paths with zero coverage:** the **entire `score` module** (all 16 files — `ScoreController`, `ScoreServiceImpl`, both sync DTOs, `ScoreEntry`, all three repositories); round setup (`round_setup_bloc.dart`, 693 lines); round start; score entry; score sync; round completion; offline package download (9 mobile + 4 API classes); refunds. `POST /rounds`, `GET /rounds`, `POST /{id}/complete` and `POST /{id}/corrections` are untested.
