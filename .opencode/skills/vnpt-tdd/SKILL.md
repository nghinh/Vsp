# vnpt-tdd

Use this skill for isolated logic implementation, bug fixes, and behavior-preserving refactors where tests can define expected behavior.

## Position in VNPT framework
Use it for core business logic, validation logic, state machines, algorithms, regression fixes, and risky refactors.

Do not use it for full feature/story development, whole-system test generation, CRUD boilerplate, simple UI changes, or duplicating tests already generated by the test orchestrator.

## TDD workflow
1. Read the issue/story/bug report and relevant docs from 0-EOF.
2. Read existing tests before creating new ones.
3. Identify the smallest externally observable behavior slice.
4. Write or update one failing test that captures the intended behavior.
5. Implement the smallest production change needed to pass.
6. Refactor while preserving green tests.
7. Repeat only for the next necessary slice.
8. Run repository-native validation commands.

## Required completion evidence
- Behavior slices covered.
- Tests added/changed with reason.
- Production files changed.
- Validation commands run and results.
- Any validation gaps clearly stated.

## VNPT operating rules
- Treat BMAD documents under `docs/` as primary project context when present: PRD, architecture, epics, stories, ADRs, test reports, domain notes, and LikeC4 files.
- Before making conclusions from any markdown/source file, read the needed file from 0-EOF. For long files, first check total line count, then read complete chunks until EOF.
- Prefer small, reviewable, repository-aware changes. Do not invent broad scope that is not supported by local docs or source evidence.
- Preserve existing framework conventions: `.opencode/skills/*`, `.opencode/commands/*`, `docs/`, `docs/stories/`, `docs/epics/`, `docs/adr/`, `docs/domain/`, and `docs/testing/`.
- When outputting artifacts, write clear markdown that another AI agent can execute without guessing.
